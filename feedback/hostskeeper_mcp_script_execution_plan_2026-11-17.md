# План: управляемый запуск скриптов через MCP

Дата: 2026-11-17
Основание: отзыв клиента о `scripts_run` и последующие уточнения владельца
Исходная ревизия: `44654c1`
Статус: этапы 0–2 завершены; этап 3 ожидает отдельной команды

## Цель

Дать MCP-клиенту достоверный жизненный цикл запуска скрипта: подтверждение
принятия, идентификатор запуска, состояние, ограниченный результат и код
завершения только тогда, когда его удалось надёжно определить. Отделить вывод и
жизненный цикл такого запуска от интерактивной работы человека в PTY, не
ослабляя аутентификацию, scope, Approve и другие действующие ограничения.

Сейчас `scripts_run` рендерит shell body и передаёт его в PTY через
`session_write`. `ok=true` подтверждает отправку, а не выполнение или успех.
Вывод приходит в общий поток сессии, который читают `session_read` и
`session_subscribe`. Это поведение описано в `doc/mcp-api.md` и реализовано в
`src/hostskeeper/mcp/service.py`.

## Обязательные инварианты

1. **Не обходить контроль выполнения.** Старт запуска сохраняет те же проверки,
   что и текущий `scripts_run`/`session_write`:
   - валидный MCP-доступ и разрешённая клиенту сессия;
   - сессия открыта человеком, имеет `target=tab` и доступна MCP;
   - целевая сессия в состоянии `live`;
   - для запуска включён session-level Approve; выключенный Approve всегда
     приводит к `approve_required`;
   - скрипт имеет `mcp_enabled=true`; host-bound скрипт доступен и запускается
     только для того же host, что и целевая вкладка;
   - проверка параметров/placeholder выполняется до любых побочных эффектов.
2. `scripts_run` не включает Approve и не создаёт новую SSH-сессию от имени
   модели. Это единственный MCP-путь для удалённого запуска сохранённых
   скриптов; произвольная команда не может передаваться исполнителю в обход
   скрипта. Сохранить соответствующие MCP tool annotations и явное описание
   потенциально изменяющего состояние эффекта.
3. Изоляция запуска отделяет его stdout/stderr и состояние от общего PTY и
   ввода человека. Для `scripts_run` разрешён отдельный SSH `exec`-channel поверх
   transport уже открытой вкладки; запуск не вставляет body или управляющие
   маркеры в общий терминальный поток.
4. Сохранить правило «человек открывает SSH-вкладку; агент только подключается
   к доступной вкладке». `exec`-channel — узкое исключение только для сохранённых
   MCP-скриптов: не открывать новый SSH/TCP transport, не получать credentials
   модели, не вводить общий произвольный exec, удалённый агент или unattended
   SSH.
5. Не выдавать exit code, пока завершение и код не подтверждены исполнителем.
   При невозможности определить исход возвращать `unknown`/`not_supported`, а
   не синтезировать успешное или неуспешное завершение.
6. Не раскрывать наличие скрытого скрипта через ошибки. Для несуществующего и
   недоступного по MCP scope скрипта сохраняется общий `not_found` с безопасной
   общей подсказкой.

## Согласованное уточнение scope — 2026-11-17

Владелец одобрил узкое исключение: запуск сохранённых MCP-скриптов выполняется
через отдельный SSH `exec`-channel поверх transport уже открытой человеком
вкладки. Это отдельный non-interactive execution context, но не новое
подключение или аутентификация и не общий remote-exec инструмент. Это уточнение
снимает архитектурный gate этапа 0; оно не является разрешением начинать
следующий этап реализации без отдельной команды.

- Общий PTY остаётся единственным интерактивным shell для человека и
  `session_write`; его ввод и буфер не используются для `scripts_run`.
- `scripts_run` запускает только сохранённый и доступный скрипт после обычных
  проверок MCP scope, `mcp_enabled`, host scope, live-состояния и Approve.
- Скрипт выполняется в отдельном shell-контексте. Не обещать наследование
  текущего каталога, переменных окружения, функций или состояния PTY.
- Контракт результата относится к процессу, запущенному SSH exec-запросом.
  Интерактивный ввод не поддерживается. Exit code этого процесса не подтверждает
  завершение/успех его фоновых потомков; для намеренно фоновых или
  отсоединённых задач нельзя обещать lifecycle и результат всей задачи.
- Таймаут ожидания, таймаут исполнения, потеря канала/сессии и подтверждённая
  отмена — разные исходы. Закрытие локального канала само по себе не доказывает,
  что удалённый процесс остановлен; `cancelled` допустим только при
  подтверждённой остановке, иначе исход остаётся `unknown`/`cancel_requested`.
- Не подменять исполнение wrapper/sentinel в общем PTY: это не даёт требуемой
  изоляции и надёжной границы результата.

2. Зафиксировать принятый путь: отдельный `exec`-channel на transport

3. Определить поддерживаемый класс скриптов. Не поддерживать интерактивный ввод
   и не обещать lifecycle фоновых/отсоединённых процессов; exit status относится
   только к процессу SSH exec-запроса, если он получен и подтверждён.
4. Описать поведение для `set -e`, `exec`, `exit`, сигналов, reconnect и потери

5. Результат: архитектура одобрена владельцем 2026-11-17. Этап 0 завершён;

   реализации. До отдельной команды следующий этап не начинать.

### Этап 1 — контракт и модель run

Контракт этапа 1 зафиксирован так:

- `scripts_run` принимает текущие selectors скрипта/сессии и `params` (без
  `submit`) и обязательный client-generated `request_id` UUID, создаёт запись
  до запуска executor и возвращает
  `{run_id, state:"accepted", accepted_at}`. `accepted` значит, что HostsKeeper
  принял запрос; это не подтверждение принятия команды SSH-сервером.
- Повторный `scripts_run` с тем же `request_id` в той же сессии возвращает
  исходный run и не запускает скрипт повторно, даже если прочие аргументы
  отличаются. Клиент обязан создавать новый `request_id` для каждого нового
  намерения запуска.
- Добавляются MCP tools `scripts_run_status`, `scripts_run_wait` и
  `scripts_run_cancel`. Status возвращает snapshot; wait ограниченно ждёт смену
  состояния/новый вывод; cancel — только запрос остановки.
- Статусы: `accepted`, `starting`, `running`, `cancel_requested`, `succeeded`,
  `failed`, `cancelled`, `session_lost`, `execution_timed_out`, `unknown`,
  `not_supported`. `succeeded`/`failed` разрешены только при полученном exit
  status; соответственно код равен 0 или ненулевой. Во всех остальных статусах
  `exit_code=null`. `cancelled` означает подтверждённую остановку.
- `session_lost` и `execution_timed_out` не означают, что удалённый процесс
  остановился; возвращать `process_may_continue=true`. Timeout конкретного wait
  отдаётся отдельным `wait_timed_out` и не меняет статус запуска.
- `execution_timed_out` означает, что execution deadline истёк, но остановка
  процесса не подтверждена. Если исполнитель подтвердил остановку по timeout,
  state становится `cancelled` с `error_code=execution_timeout`; exit code
  остаётся `null`.
- Run record содержит `run_id`, `request_id`, исходные `session_id`/`script_id`, origin
  доступа (`stdio`, `http_gateway`, `http_legacy`, без credentials/token),
  `accepted_at`, `started_at`, `updated_at`, `completed_at` (только при
  подтверждённом завершении), `state`, nullable `exit_code`, безопасный
  стабильный `error_code` и bounded output metadata. Сырые exception/SSH
  messages в запись и API не попадают.
- stdout и stderr читаются раздельно, каждый со своим cursor и `truncated`.
  `scripts_run_wait` возвращает новые порции обоих потоков; общий терминальный
  буфер не используется. Cursor привязан к конкретному run и output stream.
- Каждый status/wait/cancel сначала находит запись, затем повторно разрешает
  исходную сессию в текущем `McpAccess`; неизвестный или невидимый run
  возвращается общим `not_found`. Токен не сохраняется в run record. Проверка
  Approve нужна при старте, но не для read-only status/wait и не для cancel.
  Скрипт visibility после старта не меняет доступность записи, пока исходная
  сессия остаётся доступной клиенту.

Фиксированные v1 limits: wait default/max 30 секунд; execution timeout 600
секунд; один активный запуск на сессию и восемь на процесс; максимум 100
хранимых записей с retention 24 часа (активные не вытесняются; если лимит
достигнут до истечения retention, новый запуск отклоняется); вывод сохраняет
первые 131072 символа на каждый stream и отбрасывает последующий текст с
`truncated=true`; один ответ возвращает до 65536 символов суммарно (default
16384). Переполнение параллельных запусков возвращает `run_capacity`, запуск не
ставится в очередь. Числа и семантика входят в контракт v1; пользовательская
настройка лимитов не входит.

Полные схемы и поля ответа приведены в `doc/mcp-api.md`, runtime-модель — в
`doc/data-model.md`. Этап 1 не добавлял executor, очередь, MCP tools или
изменения поведения текущего `scripts_run`; executor и lifecycle реализованы
этапом 2, регистрация MCP-инструментов остаётся этапу 3.

### Этап 2 — безопасный исполнитель и жизненный цикл

1. Реализовать только выбранный путь: отдельный `exec`-channel поверх transport
   открытой вкладки. Не читать командный результат из общего PTY и не изменять
   ввод человека. Проверить поддержку требуемых API на минимальной версии
   Paramiko проекта и определить поддерживаемые целевые shell/ОС.
2. Связать run с исходными host/session/script и повторно enforce-ить scope и
   Approve на границе старта; новый внутренний исполнитель не должен быть
   обходом `session_write`.
3. Установить, что означает отзыв Approve при активном запуске. Рекомендуемое
   требование: после отзыва запрещать новые запуски и безопасно прекращать
   активный, если исполнитель это поддерживает; если остановка не подтверждена,
   показывать `unknown`, не `cancelled`.
4. `cancelled` выдавать только при подтверждённой остановке. Если отмена лишь
   прекратила ожидание клиента, запуск остаётся активным. Не посылать Ctrl-C в
   общий PTY как механизм отмены: это может прервать работу человека.
5. На потере сессии фиксировать `session_lost`; повторное подключение не должно
   задним числом превращать неизвестный исход в success/failure.
6. Вывод ограничить и очищать от управляющих/секретных данных согласно
   существующим правилам. Сырые ошибки исполнителя не должны содержать
   credentials, адреса или лишнее содержимое vault.

### Результат этапа 2 — 2026-11-17

- Реализован `SshShell.open_exec_channel`: отдельный канал поверх текущего
  authenticated Paramiko transport, без PTY, с немедленным EOF stdin и
  ограниченным ожиданием ответа на SSH exec request. Дополнительного TCP
  подключения или повторной аутентификации нет; закрытие вкладки закрывает и
  принадлежащие ей exec-каналы.
- Реализованы in-memory lifecycle, idempotency по `(session_id, request_id)`,
  чтение состояния/вывода, ограниченное ожидание и bounded stdout/stderr.
  Проверки `target=tab`, MCP enablement, Approve, сохранённого `mcp_enabled`
  скрипта и host binding повторяются в `SessionManager` непосредственно перед
  стартом. Внутренний `McpToolService` start path пока не зарегистрирован как
  MCP tool.
- Отзыв Approve или MCP доступа и явная отмена закрывают локальный канал, но не
  заявляют остановку удалённого процесса: исход `unknown`,
  `cancel_unconfirmed`, `exit_code=null`, `process_may_continue=true`. При
  потере вкладки фиксируется `session_lost`; reconnect не меняет старую запись.
- Исполнение ограничено 600 секундами; retained output — первые 131072 символа
  на поток, максимум 65536 символов на одну выдачу, 100 run records/24 часа,
  максимум один потенциально продолжающийся run на сессию и восемь на процесс.
  Неопределённые исходы, включая timeout/cancel/session loss, занимают capacity
  до истечения записи, так как удалённый процесс мог продолжить работу.
  Непечатаемые управляющие символы заменяются на U+FFFD. Raw SSH exception и
  command body не сохраняются в run record.
- Paramiko 3.4 source подтверждает наличие `Transport.open_session`,
  `Channel.exec_command`, `shutdown_write`, чтения двух потоков и exit status;
  локально установлена Paramiko 5.1.0. Добавлен in-process SSH integration test
  на настоящих Paramiko transport/channel: он проверяет ненулевой exit status и
  отсутствие вывода exec-канала в PTY buffer. На внешние хосты тест не ходил.
- Exec передаёт строку серверным SSH exec-правилам и shell учётной записи.
  Отдельная OS/shell portability не подтверждается: надёжный сценарий ограничен
  сохранёнными неинтерактивными скриптами, возвращающими exit status; ввод,
  background/detached процессы и Windows/PowerShell совместимость не
  гарантируются.
- Зарегистрированный MCP `scripts_run` ещё сохраняет прежнюю PTY-семантику;
  новые start/status/wait/cancel tools не добавлялись. Это остаётся этапом 3.
- Проверки этапа: unit tests executor/permissions и in-process Paramiko
  integration; live target-host test не выполнялся.

### Этап 3 — MCP-интерфейс и разрешения

1. Подключить start/status/wait/cancel в MCP-сервер с явными описаниями
   состояний и ограничений.
2. Сохранить destructive/write semantics `scripts_run`; не полагаться только
   на tool annotation — серверная проверка Approve обязательна.
3. Проверять, что host-bound скрипт запускается только в своей открытой
   MCP-enabled вкладке; шаблон запускается только в выбранной доступной вкладке.
4. Сделать ошибки видимости безопасными: одинаковый `not_found` для
   отсутствующего и недоступного объекта плюс общий hint обновить `scripts_list`
   и проверить MCP visibility/host tab.
5. Для клиента, которому запуск недоступен, дать объяснение через стандартные
   `approve_required`, `disconnected`, `client_scope` или общий `not_found`;
   не заводить диагностический ответ, подтверждающий скрытые данные.

### Этап 4 — скрытие command echo и показ результата

1. Исполнять сохранённый скрипт на отдельном SSH exec-channel, не отправляя body
   и stdin в интерактивный PTY. Не менять отдельные bounded stdout/stderr,
   cursors и lifecycle MCP.
2. Зеркалировать в общий session output buffer рамку запуска, фактический вывод
   и конечный статус. Это один transcript для UI терминальной вкладки и
   `session_read`/`session_subscribe`; у рамки указывать инициатора (user или
   MCP client). Само отображение не должно исполнять body или менять exec-контекст.
3. Сохранять пределы вывода и явно обозначать усечение. Не дублировать shell body,
   включая wrapper/команду; не фильтровать фактические строки вывода, совпадающие
   с фрагментом body. MCP `scripts_run_wait` по-прежнему возвращает stdout и
   stderr раздельно, а transcript отображает их в порядке чтения канала.
4. Явный UI-запуск сохранённого скрипта во встроенной вкладке проходит тем же
   exec-путём и получает такой же формат transcript, что и MCP-запуск. Это
   намеренно означает отсутствие наследования cwd/environment интерактивного
   shell. PuTTY остаётся внешним запуском и в session transcript не входит.

### Этап 5 — статическая валидация и обнаружение инструментов

1. Описать `scripts_validate` как статическую проверку структуры placeholders,
   объявлений параметров и готовности к подстановке. Она не исполняет скрипт и
   не гарантирует корректность для shell, ОС или конкретного хоста.
2. Обновить MCP tool description и server instructions: рекомендовать
   `scripts_validate` до сохранения/запуска draft, не позиционировать его как
   runtime/security validator.
3. Проверить обнаружение инструмента на целевых MCP-клиентах. Если клиент
   выбирает инструменты только по тексту пользовательского запроса, отдельно
   документировать client-side prompt/workaround; сервер не может гарантировать
   поведение planner клиента.

## Критерии приёмки

- Подтверждение принятия не представляется клиенту как результат исполнения.
- Exit code и `succeeded`/`failed` возвращаются только для запуска с
  подтверждённым завершением выбранного исполнителя.
- Для интерактивного, долгоживущего, фонового, прерванного или неоднозначного
  исхода возвращается `unknown`/`not_supported` или отдельное честное состояние,
  без выдуманного кода выхода.
- Исполнение отделено от человеческого PTY; UI и `session_read` показывают
  одинаково размеченный transcript запусков сохранённых скриптов для UI и MCP,
  с фактическим выводом, состоянием и без shell body.
- Отдельные MCP stdout/stderr ограничены и читаются по cursor; transcript
  отражает предел захвата и не теряет строки только из-за совпадения с body.
- MCP-запуск без Approve всегда отклоняется. Status/wait/cancel не дают способа
  начать или продолжить MCP-выполнение при обходе действующих прав; UI-origin
  run не раскрывается этим lifecycle API.
- Host script не запускается в сессии другого хоста; закрытая/не-MCP сессия не
  становится доступной через знание `run_id`.
- Отзыв Approve, отмена, timeout ожидания, timeout исполнения и потеря сессии
  имеют разные документированные исходы.
- Скрытый скрипт остаётся неотличимым от отсутствующего по MCP-ответам.
- `scripts_validate` обозначен как статический анализ без гарантии исполнения.
- Проверены модульные тесты для разрешений, scope, состояний/гонок,
  усечения/очистки, потери сессии, отмены и MCP-схем; интеграционный тест
  изолированного завершения проходит на поддерживаемых окружениях.

## Вне scope

- Исполнение скрипта на локальной машине HostsKeeper.
- Автоматическое открытие SSH-сессии моделью или установка агента на target host.

## Результат этапа 0 — 2026-11-17

### Проверенные факты

- `SessionManager` хранит один `SshShell` на вкладку. `SshShell.connect()`
  вызывает `SSHClient.invoke_shell()` для интерактивного PTY, а его reader
  направляет stdout/stderr в общий `OutputBuffer`.
- `SessionManager.write()` пишет в этот же shell channel. MCP
  `scripts_run()` сначала разрешает скрипт и рендерит параметры, затем вызывает
  `session_write()`. Этот путь проверяет live-состояние и session-level
  Approve; host-bound скрипт дополнительно ограничен host доступной сессии.
- В локально установленном Paramiko 5.1.0 `SSHClient.exec_command()` открывает
  новый SSH channel через уже существующий transport, отправляет SSH exec
  request и возвращает отдельные stdin/stdout/stderr. На channel доступен
  `recv_exit_status()`. Это не открывает новый TCP connection или повторную
  аутентификацию, но является отдельным удалённым исполнением команды.
- Проверка была статической/локальной: исходники и API Paramiko изучены без
  подключения к целевому хосту и без отправки команд на Alum. Нижняя граница
  зависимости проекта (`paramiko>=3.4`) отдельно не проверялась исполнением.

### Оценка вариантов

1. **Использовать существующий общий PTY.** Не проходит требование изоляции:
   вывод и echo неотличимы от пользовательской активности, ввод может
   перемешаться. Sentinel/wrapper не даёт универсального exit status при
   `set -e`, `exit`, интерактивном вводе и долгоживущих процессах. Вариант
   отклонён для run lifecycle с результатом/кодом завершения.
2. **Открывать второй interactive shell/PTY channel на том же transport.**
   Отделяет поток вывода, но создаёт дополнительный shell context (не наследует
   состояние интерактивного shell вкладки) и само по себе не даёт надёжной
   границы завершения и exit status для произвольного body. Также меняет
   принцип одного общего PTY на вкладку. Не подтверждено как решение.
3. **Открывать отдельный exec channel на том же уже аутентифицированном
   transport.** Технически наиболее подходящий путь для отдельного вывода и
   exit status процесса, запущенного SSH exec-запросом. Это отдельный
   non-interactive execution context, хотя новое соединение или аутентификация
   не создаются. Скрипты не исполняются в shell-контексте вкладки: `cd`/export и
   другие изменения состояния не переносятся в интерактивный shell. Exit status
   не описывает фоновых потомков, а интерактивное выполнение не поддерживается.

### Вывод и решение владельца

Первоначальная проверка этапа 0 показала, что общий PTY не обеспечивает
изолированный поток и надёжный exit status, а отдельный `exec`-channel
технически открывается поверх уже аутентифицированного transport. Владелец
одобрил узкое исключение для сохранённых MCP-скриптов, с сохранением
человеко-открытой вкладки, Approve, MCP visibility и host scope. Архитектурный
gate пройден; этап 0 завершён.

Это одобрение не означает, что исходы любого удалённого процесса можно
гарантированно определить: при потере канала/сессии, таймауте без подтверждённой
остановки или неоднозначном фоне возвращать `unknown`, а не выдуманный
exit code. Техническую совместимость минимальной версии Paramiko и целевых
shell/ОС проверить до заявления о поддержке. На момент фиксации результата
этапа 0 следующий этап ожидал отдельной команды владельца; команда на этап 1
получена 2026-11-17.
