# Требования HostsKeeper v1

## Пользователи и роли

| Роль | Описание |
|------|----------|
| Человек | Единственный оператор сейфа: vault, открытие сессий, выдача MCP |
| ИИ (MCP-клиент) | Удалённый ассистент (в т.ч. Cursor): только разрешённые Host, ресурсы и сессии |

Даже если ИИ на том же ПК, подключение к сейфу идёт по той же схеме MCP (адрес `127.0.0.1` — частный случай).

## Функциональные требования

### Vault

- Сущности: **Host**, **Address**, **Credential**, **Script**.
- У Host несколько Address и Credential; при подключении пользователь комбинирует пару (есть defaults).
- Credential: логин/пароль и/или ключ.
- Теги и описания у каждой сущности.
- Секреты человек может просмотреть только в UI (отдельная кнопка).
- Шифрование vault паролем при старте приложения.
- Импорт из Termius / SSH config — не в v1.
- Export/backup vault — позже.

### Подключения

- Цели открытия: **вкладка UI** (встроенный SSH), **PuTTY**, **WinSCP**.
- В MCP попадают **только** сессии во вкладках UI.
- PuTTY / WinSCP — только для человека, без трансляции в MCP.
- Сессию открывает **только человек**. ИИ не инициирует логин.
- На целевые устройства стороннее ПО не ставится.

### Вкладка терминала

- Свой SSH-клиент внутри сейфа (общий PTY для человека и ИИ).
- Область терминала — функциональный минимализм (содержимое совпадает с тем, что видит ИИ).
- Обрамление приложения — стиль connection manager (см. [ui-guidelines.md](ui-guidelines.md)).
- В шапке/вкладке: **alias** сессии (ручной ввод + автопредложение вида `host-user-N`).

### Доступ MCP к сессии

- MCP разрешение задаётся на Host; default off, включая Host, загруженные из старого vault без этого поля.
- Host-разрешение открывает MCP доступ к данным Host и его вкладкам. Host Script/Note дополнительно должны иметь собственный MCP-флаг; шаблоны проверяются только по своему флагу.
- Открытые вкладки разрешённого Host доступны через app key/stdio; legacy token остаётся ограничен одной вкладкой и её Host. Отключение Host MCP немедленно отзывает вкладки и их tokens.
- Approve на вкладке доступен только при включённом MCP у Host. При отзыве Host MCP Approve автоматически выключается; иначе Approve по-прежнему default off и управляет только write/run.
- В Cursor mcp.json — стабильный URL с app key; в чат — **alias** вкладки (`session_attach`).
- Наружу через MCP: без адресов, учёток, секретов. Для сессии — alias/id/status и содержимое PTY.

### Подтверждение действий (Approve)

- Чекбокс **Approve** на вкладке (default **выкл**, доступен только при Host MCP).
- Выкл → MCP только читает терминал; `session_write` / `scripts_run` сразу отклоняются (`approve_required`).
- Вкл → write/run разрешены без модалки и без таймаута.
- CRUD скриптов — без Approve.

### Скрипты

- Скрипт хранится как shell-текст; локального раннера на сейфе нет.
- `scripts_run` исполняет скрипт через отдельный SSH `exec`-канал поверх уже
  открытого человеком SSH transport вкладки. Это узкое исключение для запуска
  сохранённых MCP-скриптов, а не общий инструмент удалённого выполнения:
  модель не может открыть SSH-сессию или передать произвольную команду в обход
  скриптов.
- `exec`-канал не создаёт новое SSH/TCP-подключение и не получает отдельные
  credentials. Он отделён от интерактивного PTY, поэтому не наследует его
  состояние shell (например, текущий каталог и переменные окружения); запуск
  не предназначен для интерактивного ввода.
- Для сохранённых скриптов, запущенных человеком из встроенной вкладки или
  моделью через MCP, начало, фактический вывод и конечный статус также
  отображаются в общем буфере сессии и читаются через `session_read`. Это
  отображение не отправляет shell body в PTY и не меняет отдельный exec-контекст;
  в событии указывается инициатор. PuTTY остаётся внешним запуском.
- Код завершения относится только к процессу, запущенному SSH exec-запросом;
  он не подтверждает завершение или успешность порождённых им фоновых процессов.
- При потере канала/сессии или неподтверждённой остановке нельзя сообщать
  выдуманный exit code или успешную отмену.
- MCP-запуск требует MCP visibility, совпадения host scope, live-состояния
  вкладки и session-level Approve. Явный UI-запуск человеком требует live
  встроенную вкладку и тот же host scope, но не MCP visibility/Approve;
  MCP lifecycle не может управлять таким запуском.
- Параметры с подстановкой `{{name}}`.
- UI-формы параметров — не в v1.
- Хранение в том же зашифрованном vault.
- Чекбокс MCP у Script/Note управляет видимостью самого ресурса: новый UI-ресурс скрыт по умолчанию; host-local ресурс также требует Host MCP, шаблон — нет.
- MCP: создание / правка / удаление / список / запуск.
- `scripts_run` в выбранную/прикреплённую вкладку (gateway: alias/attach; legacy HTTP: token-сессия).

### Транспорт MCP

- **stdio** и **HTTP** сразу в v1.
- HTTP: bind на LAN, доступ по app key (gateway) или legacy tab token.
- stdio: доверенный локальный канал **без** token; видит все вкладки разрешённых Host и их MCP-включённые ресурсы.
- Пока приложение закрыто — MCP недоступен.

## Нефункциональные требования

| Требование | Решение v1 |
|------------|------------|
| Платформа | Только Windows |
| Стек | Python (ядро + MCP + SSH/PTY) + UI **PySide6** (план миграции с временного FastAPI/static: [pyside6-migration.md](pyside6-migration.md)) |
| Стиль UI | Connection manager: дерево объектов, тулбар/ribbon, вкладки сессий, status bar ([ui-guidelines.md](ui-guidelines.md)) |
| Простота / расширяемость / надёжность | Приоритет выбора технологий |
| Офлайн как цель | Не требуется (но vault локальный) |
| Облачный синк | Нет |
| Multiplayer | Нет |
| Агент на целевых хостах | Нет |

## Сценарий работы с ИИ

1. Человек включает MCP у Host и открывает SSH-вкладку, задаёт alias.
2. Копирует готовый URL в чат Cursor (или иной MCP-клиент).
3. ИИ подключается, получает alias через `session_info`, читает/подписывается на вывод, при необходимости пишет или запускает скрипты.
4. Человек параллельно работает в той же вкладке.
5. При обрыве — reconnect в UI; token и alias сохраняются, пока MCP включён.
